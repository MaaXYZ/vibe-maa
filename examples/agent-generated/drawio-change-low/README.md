# Autonomous redevelopment after a real target change

This is the **unmodified exported model submission** from [run 43208826944](https://github.com/MaaXYZ/vibe-maa/actions/runs/43208826944), source `8bb616c`: `deepseek-flash`, explicit `low`, Codex 0.167.2, **172.282 seconds / 600 seconds**. [Download the ordinary MaaFW project](../../../docs/records/archives/drawio-change-43208826944-automation.zip).

The starting project already handled the Device popup, then failed at `SplashStorage` when the real interface rendering changed. The agent received its original files, retained failure reports and labelled full frames, without a replacement template, repair coordinates or a stated cause. It reconnected to the actual application, observed and operated it, compared screenshot pixels, changed the recognition, checked its failed first parameter choice, and reran both saved task scenarios.

The independent oracle passed **12/12** fresh contexts: changed/reference rendering × blank/splash × three repetitions. It checked exactly one rectangular shape labelled `Vibe Maa`, with no modal. The original goal, templates, old screenshots and labels, and attempt budget were retained. The durable task finished `accepted/current`, two attempts used and eight remaining. The exact submission also passed **6/6** unchanged runs on the host where its predecessor had failed, and an isolated installed-wheel task execution/resumption check.

The model replaced the title template with `ColorMatch`; it did not use the separately authored diagnostic icon adaptation. The new count changed from 15000 (failed its positive cases) to 14000 (passed). **This recognition depends on the preceding `SplashOpen` branch having entered the storage dialog.** Light regions in blank and Device frames can also match it. It is not a general popup classifier, and this one development trial does not establish arbitrary UI adaptation or a success rate.

`manifest.json` and its 19 listed files are preserved byte for byte. [ORIGIN.json](ORIGIN.json) and this README are maintainer provenance outside that manifest. The inherited `verification` text in the task file is historical metadata; the new [task context](../../../docs/records/drawio-change-43208826944-task-context.json) and native evidence record actual acceptance. A newly extracted project has no runtime ledger and must be validated on its current target.

No model calls are needed to execute or replay it:

```bash
uv sync --locked --extra browser
uv run vibe-maa browser install
uv run python integration/agent/regrade.py \
  --project examples/agent-generated/drawio-change-low \
  --starting-states blank splash --repetitions 3 --output work/change-replay
uv run python integration/agent/validate_recovery.py \
  --project examples/agent-generated/drawio-change-low --output work/change-task
```

The task explicitly declares loopback port **38285** for both starts. The validation helper serves the pinned application there and uses fresh sessions, recognition-only readiness probes, actual task execution and restored context. For an installed tool outside this repository, use `vibe-maa target serve drawio --port 38285`, keep a project `daemon serve` terminal alive, open the declared URL from `task context AgentCanvas`, then `task run AgentCanvas --session SESSION --scenario blank_start` or `splash_start`. Use a new browser session for each start. Changing the URL declaration requires fresh validation.
